# Dubbing Studio — finish and verify on this Mac

## What this is

`~/Downloads/dubbing-studio` is a local video-dubbing app: paste a video link, get
the video back speaking English. It was written in a Linux cloud sandbox that
could not execute any macOS-specific code, so **the logic is tested but the Mac
integration is entirely unverified.** Your job is to make it actually run here,
fix what breaks, and confirm it works end to end.

Read `README.md` first — it documents the intended behaviour.

## Architecture in one paragraph

FastAPI server + single-page UI, shown in a native window via pywebview. The
pipeline is: yt-dlp download → Demucs splits speech from music → sherpa-onnx
diarization finds who speaks when → Parakeet (or Whisper) transcribes →
an LLM translates in batches with a domain glossary → Kokoro (or Chatterbox
cloning) synthesises each line → each line is time-fitted into the slot the
original speaker used → ffmpeg mixes the dub over the preserved music bed and
remuxes with the video stream copied, never re-encoded.

Every backend has two paths: **MLX** (Apple GPU) and **ONNX/CPU** (portable,
also used by the Docker build). `app/config.py:detect_machine()` picks. Backends
fall back rather than raise, so a missing optional dependency degrades quality
instead of failing the job.

Ordered by how likely I think they are to be broken.

1. **`Install.command` end to end.** Never executed. It installs Xcode CLT,

   `requirements-quality.txt` (torch/demucs/chatterbox — ~3 GB), then Ollama +

   ordering problems.

     `model.generate(text=, voice=, speed=, lang_code=)` yielding objects with
     `.audio`. Verify.
   - `mlx-whisper` — `asr.py:_transcribe_whisper_mlx`.
3. **Chatterbox cloning** — `app/backends/clone.py`. I assumed
   `ChatterboxTTS.from_pretrained(device="mps")` and
   `model.generate(text, audio_prompt_path=...)` returning a torch tensor, with
   sample rate at `model.sr`. Never run; the model host was blocked.
4. **Demucs** — `app/backends/separate.py` shells out to
   `python -m demucs --two-stems vocals -n htdemucs_ft -d mps`. The weights host

   shows an icon, and survives a logout.
6. **pywebview window** — `app/desktop.py`. Falls back to the browser if the

7. **A real YouTube download.** yt-dlp was never exercised against a live URL.

## Suggested order

1. Run `Install.command`, fix until it completes clean. This is most of the work.
2. `python test_pipeline.py && python test_upgrade.py` — should still pass, now
   exercising the MLX paths. Fix any API mismatches from item 2 above.
3. Short real video (2-3 min, one speaker, no music) on **Fast**. Confirm the
   output plays, is in sync, and the video stream was copied not re-encoded
   (the quality report says so).
4. Something with music and two speakers on **Balanced**. Confirm the music
   survives and the two people get different voices.
5. **Best quality** on the same clip. Confirm cloning produces the original
   speakers' voices and doesn't drift or glitch over a long run.
6. Launch the `.app` from Applications and drive a job through the window.

## Things to be careful about

- **Don't re-encode the video.** `-c:v copy` throughout. `mux.verify()` compares
  frame counts before and after; keep that honest.
- **Timing is the quality bar.** Lines must never start before their original
  timestamp. `align.assemble()` reports `max_drift` and `compressed` — on a good
  run drift is ~0 and few lines need compressing. If a change makes those numbers
  worse, it's a regression even if the audio sounds fine.
- **Fallbacks must stay silent-but-visible.** Every backend degrades rather than
  raising, and reports why through the progress callback. Preserve that: a
  missing dependency should never kill a 40-minute job.
- **Jobs resume.** Each stage caches to `~/Library/Application Support/DubbingStudio/jobs/<id>/`.
  Re-running a failed link reuses the transcription and translation. Don't break
  that — it's what makes iterating on long videos bearable.
- **Progress weights** are computed per job in `pipeline.py:_plan()` and must sum
  to 1.0 across whichever stages actually run. There's a test for it.

## Known-good reference run

A 68-minute Spanish crochet tutorial was dubbed by hand with this exact pipeline
(Parakeet → LLM translation with a crochet glossary → Kokoro `bf_emma`). Results:
830 lines, **zero timing drift**, only 7 lines needed compressing, worst squeeze
1.18x, video frames identical (123,342 in and out). That is the quality bar the
app should reproduce. The source is `~/Downloads/videoplayback.mp4` and the
finished dub is `~/Downloads/crochet-blouse-tutorial-EN.mp4` if you want to
compare.
